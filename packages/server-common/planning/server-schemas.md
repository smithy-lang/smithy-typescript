# Schema-based Server SDK — Feature Gap Analysis

Comparison of the traditional (codegen-heavy) SSDK vs. the new schema-based SSDK.

## Feature Gap Table

| ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------- |

| **Protocol: REST HTTP binding routing**        | ✅ `HttpBindingMux` with path/query matching                                                                      | ✅ `httpBindingRouter` with specificity-ranked matching                                                                                                                                               | ✓ Resolved       |

## Remaining Gaps

1. **Per-operation auth/interceptor composition** — by design, the schema SSDK uses a single service-level handler; this is a simplification, not a bug
2. **Event streams** — shared gap across both generations, not a regression

## Improvements Over Traditional SSDK

1. **Multi-protocol support** — single server handles RPC v2 CBOR, AWS JSON 1.0/1.1, and restJson1 simultaneously with automatic protocol claiming
2. **Handler request metadata** — `ServerRequestContext` provides typed access to headers, path, query, operation name, and caller identity as a separate argument (no interceptor gymnastics)
3. **Unified error hook** — `onError` replaces `ValidationCustomizer` and additionally covers auth failures and handler exceptions in one callback
4. **Schema-aware content-type validation** — skips validation for `@httpPayload` blob/string members instead of rejecting valid requests
5. **Separate handler arguments** — `handler(input, serverCtx, userCtx)` keeps framework context and user context independent, safe to evolve both without collision
